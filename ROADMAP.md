# Civil 3D MCP Production Roadmap

This roadmap moves the project from broad functional coverage to a reliable,
secure, and observable production integration. Work is ordered so correctness
and Autodesk host safety land before additional Civil 3D capabilities.

## Guiding architecture

All callers should use one authoritative path:

`MCP or HTTP caller -> schema validation -> approval policy -> host queue -> CivilExecution -> structured result`

Drawing mutations remain inside Civil 3D, under command context, document lock,
and a narrow transaction. Out-of-process services may plan, inspect, validate,
and broker calls, but must not mutate drawings directly.

## Phase 0 - Restore reliable startup and communication

Status: Complete and live-validated against Civil 3D 2026 on 2026-07-14.

Completed in the first tranche:

- Removed duplicate orchestrator registration and added a real SDK smoke test.
- Changed drawing-context collection to one plugin request per connection.
- Added immediate pending-request rejection, timer cleanup, UUID request IDs,
  response limits, plugin request limits, and plugin request-read timeouts.
- Added fail-closed non-loopback HTTP binding, origin allowlisting, timing-safe
  token checks, and authenticated loopback-only Docker publishing.
- Upgraded the MCP SDK, removed the unused direct WebSocket dependency, and
  cleared production and development dependency audits.

Live validation evidence:

- `npm run test:live-plugin` passed against plugin `1.2.1.0` on
  `127.0.0.1:8757`, including drawing context and queue/job telemetry.
- The opt-in host suite completed a legitimate QC job with a 798-byte response,
  safely below the configured 8 MiB response limit.

### Scope

- Register every MCP tool exactly once from the manifest.
- Add a real `McpServer` registration smoke test.
- Match the Node TCP client to the plugin's one-request-per-connection contract.
- Reject pending requests immediately on socket close or failure.
- Clear connection and command timers on every terminal path.
- Add request and response size limits.
- Upgrade production dependencies with known high-severity vulnerabilities.
- Fail closed when the HTTP bridge binds beyond loopback without authentication.

### Acceptance criteria

- A real MCP server registers and starts without duplicate-tool errors.
- `civil3d_orchestrate` can collect drawing context without command timeouts.
- Socket disconnects reject calls promptly instead of waiting 120 seconds.
- Docker does not expose unauthenticated drawing actions on all interfaces.
- `npm audit --omit=dev` reports no high-severity production vulnerabilities.
- TypeScript tests, TypeScript build, and the Civil 3D plugin build all pass.

## Phase 1 - Centralize safety and host execution

Status: Complete and live-validated against Civil 3D 2026 on 2026-07-14.

Completed in the current working tree:

- Added a central policy gate for every manifest-backed MCP and HTTP action.
  It derives its decision from action capabilities and `safeForRetry` metadata.
- Added `civil3d_preview_action` and `civil3d_request_approval` for the
  preview → approval → execute flow. Approval tokens are memory-only,
  single-use, short-lived, and bound to the exact parameters, tool action, and
  a hashed active-drawing fingerprint.
- Added a bounded (64 waiting operations) host gate around Civil 3D command
  contexts, document locks, and transactions. New-drawing operations use the
  same gate.
- Health now reports actual host queue depth, active operation, request ID,
  start time, and duration. Plugin dispatch logs include the JSON-RPC request
  ID generated by the Node client.
- Client disconnects now cancel queued request tokens before they enter the
  Civil 3D host gate; in-flight Autodesk calls finish at their documented
  cooperative-cancellation boundary.

Live validation evidence:

- The opt-in host suite exercised exact-parameter approval receipts for create,
  edit, delete, drawing-new, undo, and job operations.
- Four concurrent drawing queries completed through the serialized host gate;
  final readiness reported queue depth zero and capacity 64.

### Scope

- Add a central policy service that consumes action capabilities and
  `safeForRetry` metadata before execution.
- Implement `preview -> approve -> execute` for destructive or ambiguous work.
- Bind approval tokens to drawing fingerprint, tool, action, parameters, and an
  expiration time.
- Serialize host operations through a bounded `Channel<T>` or equivalent queue.
- Report real queue depth, active request, duration, and correlation ID.
- Propagate caller cancellation to queued work and clearly report operations
  that the Autodesk API cannot interrupt once started.

### Acceptance criteria

- Delete, overwrite, import, save, new-drawing, and standards-remediation actions
  cannot execute without the configured approval policy.
- Concurrent callers produce deterministic, serialized host execution.
- Cancelling queued work prevents it from entering a Civil 3D transaction.
- Every call has an end-to-end request ID in Node and plugin logs.

## Phase 2 - Harden filesystem and network boundaries

Status: Implemented in the current working tree

Completed in the current working tree:

- Added one plugin-side filesystem boundary that canonicalizes paths, rejects
  traversal and reparse-point escapes, enforces configured import/export roots,
  and applies operation-specific extension allowlists.
- Generated reports use same-directory temporary files plus atomic replacement;
  every exposed writer defaults `overwrite` to false.
- HTTP requests now require an allowlisted `Host`, retain the explicit browser
  `Origin` allowlist, and reject wildcard host/origin configuration.
- HTTP failures use stable `{ error: { code, message } }` bodies and map domain
  validation, authentication, not-found, unavailable, conflict, and timeout
  errors to their corresponding statuses.
- Plugin JSON-RPC errors use numeric JSON-RPC 2.0 codes while retaining the
  stable `CIVIL3D.*` identifier in `error.data.code`; the Node client validates
  this envelope and preserves it through MCP and HTTP dispatch.

### Scope

- Canonicalize import and export paths and enforce configured roots.
- Add per-tool extension allowlists and `overwrite: false` defaults.
- Use temporary files and atomic replacement for generated artifacts.
- Validate HTTP `Host` and `Origin`; replace wildcard CORS with an allowlist.
- Map validation, authentication, not-found, unavailable, conflict, and timeout
  failures to stable HTTP and domain error codes.
- Use numeric JSON-RPC error codes and retain `CIVIL3D.*` identifiers in
  `error.data.code`.

### Acceptance criteria

- Path traversal and writes outside configured roots are rejected.
- Existing files are not overwritten without explicit permission.
- Non-allowlisted browser origins cannot invoke the bridge.
- JSON-RPC responses validate against the JSON-RPC 2.0 error shape.

## Phase 3 - Adopt richer MCP contracts

Status: Complete and live-validated through a production stdio MCP client on 2026-07-14.

Completed in the current working tree:

- Replaced deprecated `server.tool(...)` registration with the SDK's
  first-class `registerTool(...)` API across the manifest and approval tools.
- Added action-aware `outputSchema` contracts and matching
  `structuredContent` while preserving text content for older clients and the
  HTTP bridge.
- Derived MCP read-only, destructive, idempotency, and open-world annotations
  from the same capabilities, retry metadata, and approval rules used by the
  central policy gate.
- Kept the default surface compact at one canonical tool per domain plus the
  orchestrator; specialized aliases remain opt-in.
- Added MCP resources for the tool catalog, host-safety guidance, framework
  standards, and bounded short-lived report/export results.
- Added progress notifications for clients that supply an MCP progress token.
- Added real in-memory MCP client coverage that lists typed tools and resources,
  reads resources, and validates the compact default surface.

Live validation evidence:

- `npm run test:live-mcp-client` passed with 33 public tools, typed schemas and
  annotations, three progress notifications, and a readable
  `civil3d://reports/...` resource.
- Live health and drawing-info actions passed through the spawned stdio client.

### Scope

- Move registration to the SDK's first-class `registerTool` API.
- Return `outputSchema` and `structuredContent` for typed tool results.
- Translate catalog metadata into MCP read-only, destructive, and idempotency
  annotations.
- Reduce the default tool surface to canonical domain tools; make specialized
  aliases opt-in.
- Expose documentation, standards, catalogs, and large reports as MCP resources
  or resource links.
- Send MCP progress notifications for long-running work.

### Acceptance criteria

- Priority domains have strict response schemas rather than empty passthroughs.
- Tool annotations agree with central policy metadata.
- A default client receives a compact tool set without losing domain coverage.
- Long operations report progress without polling-only UX.

## Delivery rule

Do not add another domain-wide tool family until Phase 0 is complete. New work
after Phase 0 must include its schema, policy classification, structured result,
and the narrowest useful regression test.

## API-first remediation track

Status: Complete and live-validated against Civil 3D 2026 on 2026-07-14.

Completed in the current working tree:

- Native `getProjectContext` replaces three sequential drawing-context RPCs.
- Alignment report station sampling is one typed, batched plugin command.
- Documented alignment, profile, surface, parcel, drawing-settings, surface
  analysis, terrain-statistics, and volume APIs are called directly.
- The compatibility boundary caches version-dependent member/type resolution;
  common object helpers no longer resolve reflection themselves.
- Silent engineering substitutes were removed from slope, surface analysis,
  volumes, section export, plan production, and widening transitions.
- Default MCP registration is compact; specialized aliases are opt-in through
  `CIVIL3D_ENABLE_TOOL_ALIASES=true` while remaining internally routable.
- Direct reflection has been removed from command modules. A boundary test
  enforces `Civil3DCompatibility` as the sole cached, version-dependent
  reflection boundary.
- Intersection, assembly, gravity/pressure network, survey, grading, plan
  production, and quantity commands now use documented typed APIs where the
  2026 managed API supports the operation. Unsupported or unprovable behavior
  fails explicitly instead of returning fabricated engineering values.

Live validation evidence:

- The host suite created two disposable TIN surfaces, added vertices, called
  the documented `TinVolumeSurface.Create(String, ObjectId, ObjectId)` path,
  received exact volume properties, and proved the temporary volume surface was
  absent after the read transaction aborted.
- The same suite live-proved query, mutation, parameter-bound approval, cleanup,
  and cancellation behavior.
